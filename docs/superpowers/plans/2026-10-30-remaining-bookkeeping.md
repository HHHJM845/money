# 收支记账剩余工作实施计划

> **For agentic workers:** 使用 superpowers:subagent-driven-development 或 superpowers:executing-plans 按阶段执行。沿用用户已授权的 subagent/worktree 并行方式；主代理负责契约、SQL 集成、审查和验收。

**Goal:** 在已验证的账务内核和 Web 核心之上，交付一加 13 可安装、手机电脑联网同步、支持自动采集和人工纠错的个人收支账本。

**Architecture:** Android 使用 Room 保存本地账单和持久操作队列，界面观察本地 Repository；服务端统一处理账务事务、版本和提交顺序，两个客户端消费增量变化。采集、文件和 AI/OCR 均进入同一候选及入账流程。

**Tech Stack:** 现有 Kotlin/Compose/Room、React/TypeScript、Vercel Functions/PostgreSQL；后台同步使用 WorkManager。新依赖只在所属任务核实后引入。

## 约束与当前状态

- 沿用已批准的 84 项决策与 `2026-10-30-auto-bookkeeping-design.md`；阶段交付不删减首版范围。
- 单人、单账本、人民币；账单/统计/我的三导航，不恢复股票或投资看板。
- M1 已完成；P1 的服务端、Web 和 Android 工程验收通过。完整首版和一加 13 真机验收尚未完成。
- 已验证：Node 89 项测试、Web 构建及隔离浏览器流程；Android 118 项测试、lint 和新版测试 APK 构建；真实 PostgreSQL 17.11 独立多连接 9 项验证。详见 `../../testing/2026-10-30-bookkeeping-execution.md`。
- 未验证：一加 13 实际安装、系统键盘、支付识别、权限和后台运行，以及生产部署后的双端同步。当前 APK 是调试签名的 P1 工程测试包。
- 不重做已完成模块，不丢弃现有未提交或未跟踪文件；不自动提交、推送或执行生产 SQL。
- 金额、退款、实际余额影响、来源、版本及幂等规则以 `../../contracts/bookkeeping-v1.md` 为准。
- 服务端结构变更同时维护 `doc/sql/init.sql` 和追加 `doc/sql/increment.sql`；Android 对应 SQL 放 `doc/sql/android/`。中文注释、无外键、不建框架迁移文件。
- 不修改域名、连接、秘密、认证或环境配置；若实施确需变更，先说明具体影响并取得相应授权。
- AI 服务商/模型与费用上限未指定，仅阻碍真实 AI 联调和对应最终验收，其余任务继续。

## 交付顺序

| 顺序 | 交付物 | 可观察的完成标准 |
|---|---|---|
| P1（工程验收通过） | 双端记账同步测试 APK | 本地持久化重开、真实接口回放及原生界面通过；设备安装、实际杀进程和线上双端演示待验收 |
| P2 | 自动采集测试 APK | 已验证支付场景产生正确账单或待确认；重复来源不重复扣账；失败和遗漏可诊断 |

## P1：先完成双端账本

### 1. 冻结同步和本地事务契约

**范围：** `docs/contracts/bookkeeping-v1.md`、`server/bookkeeping.ts`、`server/http.ts`；新建 `server/sync.ts`、`server/sync.test.ts`。

- [x] 明确初次快照、分页增量、提交确认、冲突、删除标记和游标失效的返回形状；序号继续使用整数串。
- [x] 当前账户、分类、标签使用同一提交顺序；后续预算等主数据继续接入此序列，不能只同步账单。
- [x] 明确快照与首个增量衔接：快照序号和数据同一一致性视图，不能漏掉中间提交。
- [x] 固定余额基线语义：启用余额不重放旧账；校正有历史记录；旧账仅改备注不重新扣款。
- [x] 服务端/浏览器两个客户端覆盖同版本并发、响应丢失、分页中断、旧日期补记、删除后旧设备回传；独立 PostgreSQL 多连接验证锁及提交顺序。Android 回放在任务 2 继续验证。

**门槛：** 契约与测试先收口，再让 Android 和 Web 分别对接。真实多连接测试使用隔离数据库，不使用生产账本。

### 2. Android 持久账本与操作队列

**范围：** `android/app/src/main/java/fun/huangjiamu/money/data/LedgerDatabase.kt`，新建同目录 `LedgerRepository.kt`、`SyncRepository.kt`、`SyncWorker.kt`；对应测试放 `src/test` 或需设备的 `src/androidTest`；维护 `doc/sql/android/`。

- [x] 扩展本地账单、账户、分类、标签、实际余额影响、历史、来源、云端版本和游标。
- [x] 同一次 Room 事务保存本地业务变化与待上传操作；网络调用不能放进本地数据库事务。
- [x] 持久化操作 ID、完整请求、预期版本、结果未知/失败/冲突状态；发送后内容冻结。主数据另有持久请求日志和重启恢复入口。
- [x] 同一账单连续编辑保留依赖顺序；冲突暂停该依赖链，无关账单可继续同步。
- [x] 增量整页落库后才推进游标；云端确认按操作匹配，不覆盖后续尚未上传的本地编辑。
- [x] 前台立即同步、后台可重试；登录过期有独立状态并保留队列，安全会话存储遵循现有认证边界。WorkManager 已接入，真实后台运行仍待设备验证。
- [x] 保留旧试验库中的待确认记录及来源，验证升级失败回滚，禁止以清库代替升级。

**门槛：** 离线保存后进程重启、提交成功但响应丢失后重试，都只产生一笔账及一次余额影响。

### 3. Android 三导航与双端管理

**范围：** Android `ui/MoneyApp.kt`、`ui/EntrySheet.kt`、`ui/SettingsPage.kt`、`MainActivity.kt`，按职责新增详情/待确认/统计页面；Web `src/App.tsx`、`src/SettingsPage.tsx`、`src/bookkeeping-api.ts`、`src/styles.css`。

- [x] Android 对接 Repository，实现账单/统计/我的、月份与筛选、待确认、编辑/删除/恢复/退款及来源详情。
- [x] 手机电脑补齐账户管理、余额启停/校正、分类层级和标签管理；停用后旧账仍可读，非法新引用明确报错。
- [x] Web 将可见时全量轮询替换为增量更新，焦点恢复立即拉取；原有结果未知重试及冲突保留输入不可退化。
- [x] 明确待同步、同步中、失败、冲突和登录过期；失败表单保留输入，不把本地保存显示为云端成功。Web 刷新和 Android 重启后可恢复原设置请求，保存日志失败时不发送。
- [ ] 检查手机大字体、键盘遮挡、深浅主题及桌面布局；原生界面用原生测试/截图验证。已通过桌面/360px 浏览器及 360dp 深色、1.3 倍字体的原生合成渲染，实际系统键盘与设备布局待验。

**P1 演示脚本：** 手机断网新增支出 → 杀进程重启 → 联网电脑出现 → 电脑修改分类 → 手机收到 → 手机删除、恢复、部分退款 → 双端余额、净支出、历史一致；再制造同版本冲突并解决。

## P2：自动采集进入同一账务流程

**范围：** Android `capture/`、`data/CaptureStore.kt`、P1 Repository；新增 `docs/testing/android-capture-matrix.md`。

- [ ] 保留通知与可选无障碍两个独立开关，说明权限实际用途和后台状态。

- [ ] 先打通微信、支付宝、招商银行、掌上生活，再完成云闪付、淘宝、京东、拼多多、美团；九应用范围保持不变。

- [ ] 已验证规则且必需字段明确、无重复冲突时自动入账；其他结果进入待确认，不改变余额或统计。

**P2 门槛：** 合成解析测试通过后交付测试 APK；实际覆盖按应用/版本/场景报告。“列入白名单”和“编译通过”不能作为支持证明。用户主动完成真实付款，不由代理代付。

**范围：** 新建 `server/ai.ts` 及测试；Android 新增文字入口、系统图片选择与本机 OCR 适配器。

- [ ] 云图片仅上传用户主动选择的本次图片；文字/图片结果不直接成为已确认账单。
- [ ] 未配置、超额、网络失败和字段歧义可见；密钥仅服务端，费用校验由服务端执行。

- [ ] 恢复前预览、校验引用及金额、备份现状并协调暂停同步；恢复失败保留原状态。

## 并行边界与下一步

1. 主代理先收口 P1 同步与余额基线契约，同时补真实数据库并发验证。
2. 契约稳定后，子任务 A 负责 Android 存储/队列，B 负责服务端增量和主数据事务；SQL 由主代理集中集成。
3. Repository 接口稳定后，子任务 C 负责 Android 页面，D 负责 Web 管理和增量展示，不同时修改公共契约。
4. P1 验收后分应用适配器并行采集开发；跨入口身份、自动入账和账务事务保持统一负责人。
5. 每个检查点更新实际测试记录和未完成项，不用完成计划代替完成产品。

本轮已生成 P1 测试 APK 与原生到真实接口的双端回放记录。下一步是 P2 结构化采集、未知发生时间持久化与统一候选队列；实际识别、后台和线上同步仍按设备及发布门槛分别验收。
