# 安卓自动收支记账：重做方案与实施计划

日期：2026-10-29。状态：方案提案，未开始重写、未替换线上版本。

## 1. 已确认目标

- 只为本人使用，主要设备为一加 13；先做 Android App，电脑网页作为辅助。
- 只做收支记账，移除股票、证券持仓、投资收益、资产增长看板和理财功能。
- 核心价值是自动收集支付信息、减少漏记和重复记账；手动记账和导入用于补漏。
- 首批来源：微信、支付宝、招商银行储蓄卡/信用卡。
- 用户已接受通知读取及后台运行，现确认接受可选无障碍作为方案。实际权限仍需用户在设备上主动授予；不等于已开启。
- 不默认引入 Root、Xposed、Shizuku、短信读取或持续录屏。分享截图识别另按实际使用授权。
- 延用 Vercel + Supabase PostgreSQL 作为云端候选基础设施，保留已有账单。UI 与产品流程重建，不清库、不覆盖现有数据。

## 2. 本轮竞品依据

本轮查阅官方产品页、使用手册与开源仓库；没有安装竞品或在一加 13 上实测，不把厂商功能描述当作覆盖率证明。未查询或承诺具体订阅价格。

| 参照 | 已查到的机制 | 本产品采用的思路 |
| --- | --- | --- |
| 钱迹 | 以简洁记账为定位；Android 自动记账使用无障碍读取支付页，付费功能，后台服务/页面适配影响识别 | 账单优先，分类与金额直达，避免理财入口；权限与采集状态可见 |
| 一木记账 | 支付结果/详情页识别，弹窗确认与极速模式，商户修正记忆、已识别账单列表；官方说明银行 App、无成功页面的代扣等有覆盖盲区 | 自动收集、低成本确认、用户修正能复用，漏记有补录路径 |
| Copilot Money | 交易核对、搜索筛选、详情编辑、拆分和周期标记 | 学习核对与纠错流程，不假设其金融机构连接可用于国内账户 |
| AutoAccounting | 开源自动记账项目，包含多种采集渠道与屏幕识别，GPL-3.0；部分能力涉及 Xposed/Root/Shizuku | 研究采集与规则分离，作为适配参考；不为复用代码默认引入高权限或整套架构 |

官方资料存在版本差异：钱迹旧 FAQ 曾写不考虑自动记账，当前专门的 Android 自动记账文档已描述该功能，应以当前功能文档为准。

## 3. App 与网页分工

推荐 Android 原生 Kotlin + Jetpack Compose，使用 Material 3 成熟组件；Room 保存本地账本与待同步任务，WorkManager 执行可重试同步。通知监听和无障碍由系统服务承担，不用定时后台任务冒充实时采集。

备选 Flutter 也可做，但这些安卓采集能力仍需原生实现；当前没有 iOS 目标，不优先增加桥接维护。纯 Web/PWA 能做导入、核对与统计，但浏览器通知 API 不能监听微信、支付宝等其他 App 的系统通知，也不能取得其无障碍页面节点；封装网页本身不会获得这些能力。

- App：识别、离线保存、快速确认、手动补记、提醒、日常查看。
- 网页：批量整理、历史文件导入、搜索、导出、长周期统计。
- 云端：设备同步、账本备份和查询；不能代替手机采集其他 App。
- App 登录/设备凭证需单独设计，不能把数据库密钥或服务端签名密钥打包进 APK。实施鉴权调整前明确兼容方式与环境影响。

## 4. 自动记账链路

```text
通知 / 允许的支付结果页 / 用户分享账单 / 文件导入
  → 本地收集事件 → 提取金额、时间、商户、支付账户线索
  → 匹配交易、查重、分类 → 待确认或自动入账
  → 可修改/撤销的正式账单 → 离线队列 → 云端同步
```

事件与正式账单必须分开。同一笔交易可以关联多条来源证据，不能每收到一条通知就新增一笔账。

### 分层采集

1. 通知读取：只处理用户勾选的支付/银行应用。收到包含交易信息的通知才能识别；通知未发出、被隐藏或字段不全不能猜测。
2. 可选无障碍：仅适配白名单应用的支付成功页、账单详情页。只读节点，不自动操作支付、不采集聊天或密码，不以关闭支付保护为运行前提。
3. 用户主动分享截图/文字：作为后续补漏入口；优先本机 OCR，不默认把截图发给外部 AI。
4. CSV/XLSX：补历史账单与对账。导入与自动采集共同查重，不能形成两套互不相识的流水。

首轮自动收集进入待确认，建立真机样本集。用户启用自动入账后，仅对验证通过、金额/方向/账户明确且无重复冲突的规则直接入账；其他记录保留待确认。不能每笔强制打开表单，也不能把不完整数据当成完整消费。

招商银行与信用卡覆盖要看实际通知内容；如果只能收到短信，现有通知方案不等于短信读取，需另评估权限或继续用账单导入。

### 资金与查重规则

- 微信/支付宝是交易来源，不一定是实际资金账户。无法识别使用哪张卡时，保留待确认，不能默认记为零钱支出。
- 同金额、相近时间只是疑似重复，不足以自动删除或合并；优先使用交易编号、渠道与账户证据。
- 通知更新、页面再次打开、断网重试、历史文件重传必须幂等。
- 信用卡消费计入支出，还款记为转账；两者不能重复计入支出。
- 退款关联原支出，支持部分退款；实际到账时体现退款及净支出，避免伪装成工资等普通收入。未匹配原交易的退款待确认。
- 手动修正分类可形成明确可编辑的商户规则；不能悄悄改变历史账单。
- 编辑、删除、撤销及错误合并恢复必须是首版能力。处理删除同步与跨端修改冲突，防止旧数据重新出现。
- 待确认记录不进入正式收支统计；页面标注统计仅覆盖已入账交易。

## 5. 新 UI：按手机任务设计

以原生列表、底部操作面板、分类选择器、数字键盘和标准导航为基础，先做浅色主题。稳定使用一种主色；金额、日期、商户是视觉重点。不使用桌面侧栏缩小版、巨型指标卡、营销文案、未实现功能占位。

主导航：账单 / 待确认 / 统计 / 我的。

### 账单（默认页）

- 顶部月份与搜索，紧凑显示本月支出、收入、结余。
- 按日期排列，显示商户、分类、金额，来源用次级标记；有不确定项才显示待确认入口。
- 记一笔入口始终容易触达。点交易即可修改，不走多层弹窗。

### 待确认

- 展示识别结果及具体原因：账户未知、疑似重复、退款待关联等。
- 单笔确认/修改/忽略；仅对适合同一种处理的记录提供批量操作。
- 无待处理时只显示简洁空态。自动入账成功默认不弹打断支付的大窗口。

### 统计

- 月收入、月支出、分类排行与简单趋势；点分类进入对应流水。
- 区分支出、退款和净支出；同周期比较，不用不完整账单推算真实总消费。
- 预算、周期订阅识别后置，不进入第一版。

### 我的

- 支付账户与分类、自动采集设置、导入导出、同步备份。
- 采集状态分别显示权限、服务连接、最近收到事件、最近识别成功、待同步数量。不能用一个绿点宣称所有账单都已收齐。
- 账户用于归属与转账，当前余额可选填；不再要求先维护完整资产表才能开始记账。

首次使用：建立本机账本 → 选择常用来源 → 按需授权 → 做一笔可核对的识别测试 → 可选登录云同步。拒绝某项权限仍能手动记账及导入。

## 6. 实施阶段与验收

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| 0 采集可行性验证 | 可安装的最小测试 APK、来源/场景覆盖表 | 在一加 13 确认系统与支付 App 版本；验证实际通知/节点可见性，记录可采、缺字段及不可采的场景，不以模拟通知替代真机结果 |
| 1 流程与 UI 原型 | 账单、待确认、记一笔、采集设置四条可点击流程 | 用户确认日常路径、信息密度、按钮位置后再实现完整页面；样例数据明确标识 |
| 2 可离线使用的记账 App | 收支、转账、分类、搜索、编辑删除撤销、本机存储 | 无网络可完整操作；进程重启后数据仍在；消费/还款/退款统计符合测试样本 |
| 3 自动收集与核对 | 通知/可选无障碍适配、事件队列、查重、确认规则 | 真实场景中重复通知/页面重进不新增；识别失败可定位；用户确认过的规则可选择自动入账 |
| 4 云同步与电脑端 | 复用经验证服务端能力、导入对账、跨端查询 | 断网恢复不重复，编辑删除能同步，冲突不静默覆盖；备份恢复演练通过 |
| 5 日常试用 | 连续 7 天核对报告与修复清单 | 核对约 30–50 笔真实流水及异常样本；金额/方向错误和重复入账逐项修复，再扩大自动入账范围 |

阶段 0 与 1 可并行；未验证采集能力前不完成整套视觉重写。阶段 3 正式自动入账依赖阶段 2 的纠错能力。安卓采集、账本规则、视觉原型可分工，数据契约确定后再并行编码。

测试矩阵包括：微信/支付宝扫码、付款码、前台/后台/锁屏、通知隐藏、信用卡消费与还款、免密代扣、全部/部分退款、同金额连续两笔、同一交易多渠道通知、重复文件、断网/重启/省电/权限撤回。受阻场景降级为分享或导入，不以削弱支付保护为验收条件。

分别记录两类指标：①手机确实收到可读信息后的识别正确率；②与完整银行/支付账单对比的总覆盖率。不能把第一项冒充第二项。目标是已验证样本内金额方向正确、无重复正式入账，未覆盖情况有明确补漏入口；不承诺全场景 100% 自动。

## 7. 复用边界与数据保护

- 保留既有网站作为过渡版、原账单与数据库备份；新 App 就绪后再切换。
- 复用现有整数分金额、收支/转账测试、解析器与服务端事务经验；现有接口并非已完成离线同步，需增量设计。
- 本轮没有修改代码、数据库结构、域名、凭据或部署配置。后续结构变更按项目规则同步维护 init.sql 和增量 SQL，并先在独立测试库验证。
- 开源项目按模块评估；AutoAccounting 的 GPL-3.0 不能当无条件复制许可，正式复用前确认具体文件许可、衍生发布方式与更新维护成本。钱迹和一木作为产品参照，不假定源码可用。
- 原始采集内容仅保留必要支付字段，本地敏感内容应有保护与清理策略；默认云同步结构化账单，不上传完整通知/屏幕内容。
- 第一版私用签名 APK；安装来源限制、后台策略和权限引导在本人手机上验证。若以后公开发布，另评估应用商店要求，不将私用验证当成上架审核通过。
