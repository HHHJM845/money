# 个人收支与资产管理方案

日期：2026-10-29  
状态：已确认需求的设计稿；开源接口已做静态核实，尚未完成应用运行和手机实测。

## 目标与成功标准

为个人构建收支记账和资产统计产品。一加 13 负责尽可能自动捕获交易，服务器统一保存数据，手机和电脑均可访问。通知无法覆盖的交易允许通过文件、图片或手动补录。

首期成功标准是：一笔有效交易经采集或导入后，正确进入账本；网络重试不新增重复账单；无法判断的内容可见、可处理；网页可以查看入账结果。完整资产估值和投资分析分阶段交付。

## 已确认需求

| 项目 | 结论 |
| --- | --- |
| 使用者 | 个人，不预建家庭、团队或收费体系 |
| 设备 | 一加 13；电脑与手机网页 |
| 数据保存 | 自有服务器保存并同步 |
| 支付账户 | 微信、支付宝 |
| 银行与信用卡 | 招商银行卡、招商信用卡 |
| 投资 | 华泰证券 A 股 |
| 输入 | 自动采集为主，兼容主动导入、手动录入 |
| 已接受的权限 | 通知访问、后台运行 |
| 未确认的权限 | 短信读取、无障碍、屏幕捕获、Shizuku、Root |
| 期望指标 | 收支、结余、资产、负债、净资产、分布、趋势、投资盈亏及年化收益 |

接受通知访问不等于接受其他权限。首期不把额外授权作为可用条件。

## 路线比较

| 路线 | 收益 | 成本与边界 |
| --- | --- | --- |
| 复用 ezBookkeeping，适配安卓采集端（推荐） | 复用成熟账本、报表和国内导入器 | 需要实现采集到服务端的可靠衔接，A 股仍需扩展 |
| 复用整套安卓记账生态，再补网页 | 手机上手可能较快 | 自有服务器、网页和数据模型受目标记账软件约束 |
| 自建完整账本与客户端 | 数据和界面自由度高 | 重做账户、统计、导入和账务校验，初期成本最高 |

推荐先验证第一条路线。AutoAccounting 是采集候选，不等于已经选定其全部模块或已具备直连能力。

## 架构与职责

```text
一加 13
  指定应用通知 -> 本地识别 -> 持久待上传队列
                                  |
                                  v
                         采集与导入接入层
文件 / 图片 / 手动录入 ----------> 校验、规范化、来源记录
                                  |
                         去重判断 / 待确认
                                  |
                                  v
                         ezBookkeeping 账本
                                  |
                         电脑网页 / 手机网页
```

接入层是独立职责，不预先决定必须另起一个服务。先通过集成验证判断：扩展上游服务或使用轻量适配服务，哪种对现有账本修改更少。

手机只处理用户选择的应用。原始通知默认留在设备端，只上传记账所需字段；避免把验证码、消息正文或完整卡号带入账本、日志和错误信息。跨设备所需凭据通过受保护的配对流程提供，不写死在 APK 或源码中。

## 数据入口

| 入口 | 首期安排 | 扩展条件 |
| --- | --- | --- |
| 通知 | 验证微信、支付宝、招商银行、招商信用卡；允许增选应用 | 每个来源以实机通知内容决定覆盖率 |
| 文件 | 优先复用微信 CSV/XLSX、支付宝 CSV 解析器 | 招商与华泰按实际导出格式适配，不预设列名 |
| 手动录入 | 复用账本录入能力 | 支持修改、补记与余额核对 |
| 图片 | 保留为扩展入口，识别结果先确认 | 确认识别方式与数据去向后接入 |
| 短信 | 非首期必需条件 | 另行授权并确认系统兼容性 |
| 屏幕识别 | 通知覆盖不足时评估 | 明确授权和触发方式后验证 |

应用内的支付成功消息不一定会产生 Android 系统通知。扩大应用范围不能解决来源本身没有通知的问题。

## 交易与状态

接入记录包含：设备生成的事件 ID、来源类型、应用标识、源记录 ID（可得时）、发生时间、捕获时间、金额、币种、收支方向、商户、账户映射、规则版本和处理状态。

金额使用精确十进制或整数最小货币单位处理，不能使用浮点计算账务。事件 ID 在重试时保持不变；相同文本的新通知不能直接视为同一个事件。

处理状态覆盖：

- 本地待上传、上传中、服务端已接收、上传失败可重试。
- 服务端待确认、待入账、已入账、确认重复、已忽略、入账结果未知。
- 文件待解析、解析失败、预览待确认、部分完成、全部完成、撤销中、已撤销。

服务端已接收不代表账本已入账。客户端和页面必须显示可区分的结果；异常需有原因和重试入口。

## 去重和恢复

1. 同一设备事件 ID 的重传返回已有处理结果，不重复创建交易。
2. 同来源有可靠订单号或流水号时，按用户、来源和源记录 ID 判断重复。
3. 金额、时间、商户仅作为疑似重复线索。缺少可靠关联时进入待确认，不自动吞掉同商户同金额的两次真实消费。
4. 支付平台和银行卡通知可以对应一次消费。匹配后保留多个来源，账本只保留一次消费。
5. 入账请求超时后先核对是否已成功，不能直接当失败重建。上游短期重复提交检查不是永久去重记录。
6. 修改过或确认过的账单不因后续导入而被静默覆盖。

接入记录与上游账单 ID 建立持久映射。适配层崩溃、服务重启和失败恢复必须纳入验证；跨服务写入无法靠本地唯一键自动获得原子性。

## 文件导入

文件上传后先解析并预览，显示新增、疑似重复、无效及忽略条数。用户确认后再写入，显示成功与失败数量，不能把部分完成显示为全部成功。

同一文件重复上传识别为已导入批次；不同导出时间范围可能重叠，仍需记录级匹配。无源记录 ID 时不能仅凭文件哈希处理所有重复问题。

撤销仅作用于本批新建且未被后续修改的账单；不能删除先前存在、仅被关联的交易。已被修改的记录提示人工处理。该批次管理能力需要验证或扩展，不能当成上游现成能力。

## 账务口径

- 微信零钱、支付宝余额、招商银行卡分别是账户；微信或支付宝只是支付通道时，应计入实际扣款账户，不能同时扣减两个余额。
- 信用卡额度不是资产。消费形成支出和负债，还款是资产转移并减少负债；利息与手续费单列支出。
- 账户转账不计入日常收入或支出。
- 退款优先关联原消费并冲减相应支出，不能简单当作工资等收入。
- 证券账户现金与股票市值分别管理，银证转账不计入日常收支。
- A 股买卖属于投资交易，不直接作为日常消费和收入；交易费用与分红需有明确口径。
- 余额调整与资产估值变化不当作日常收支；净资产走势包含估值日期和数据更新时间。

这些口径是目标行为，仍须验证上游账户类型、退款和统计能力能否直接表达；不兼容时记录差异后再确定改动范围。

## 资产与 A 股

期初余额和当前欠款由用户录入或用可靠文件核对。自动采集的流水只覆盖部分变化，不能据此承诺资产始终准确。

华泰证券按三个数据集合适配：持仓快照、成交记录、资金流水。先根据实际可导出文件定义列映射，复用可靠标识防止重复导入。持仓快照是指定日期的状态，不等于新增买卖。

第一阶段可手动更新持仓估值并显示更新时间。行情服务尚未选定，不承诺实时行情，也不把券商登录信息交给采集端。

完整盈亏和年化收益计算需要资金进出、买卖、分红、费用及估值记录。数据不足时展示可计算的指标和缺失项，不生成看似精确的年化收益。

## 交付顺序

1. 完成开源源码可行性报告与本方案。
2. 运行账本候选，使用虚构数据验证创建交易、账户、鉴权和重复提交边界。
3. 通过统一接入入口和导入入口实现持久状态、预览、确认、去重和失败恢复。
4. 构建安卓候选采集端，在一加 13 上验证通知内容、锁屏、离线、重启及后台限制。
5. 适配实际招商账单和华泰文件，完善资产与投资统计。

各阶段独立验证，不以全部功能完成作为首个可用版本的条件。

## 验收场景

| 场景 | 通过标准 |
| --- | --- |
| 一次有效消费 | 正确金额、方向、时间和账户进入账本，网页可查 |
| 相同事件重传十次 | 只新增一笔，返回同一处理结果 |
| 同商户相同金额连续消费两次 | 两笔均保留，不因文本相同被误删 |
| 微信银行卡支付产生两个来源 | 可确认关联为一笔消费，两个来源可追溯 |
| 上传离线、应用重启 | 未完成事件仍可恢复上传 |
| 上游写入成功但响应丢失 | 不盲目重建，显示核对状态并恢复已有账单关联 |
| 不完整通知 | 进入待确认，不能擅自猜测账户入账 |
| 同一账单文件再次上传 | 不重复新增已确认记录 |
| 文件导入中途失败 | 显示实际成功与失败数量，可按记录恢复 |
| 撤销导入 | 只处理本批可撤销交易，不损坏原有记录 |
| 信用卡消费与还款 | 消费只计一次支出，还款不再计消费 |
| 银证转账和买卖股票 | 不污染日常收支，证券现金与持仓不重复统计 |

手机覆盖率以“实际捕获有效交易数 / 对账确认的交易数”报告，同时统计误记、重复和待确认数量。通知覆盖率与识别正确率分别计算，当前不承诺固定百分比。

## 本轮验证边界

本轮完成上游源码与许可证静态核实。没有连接手机、获取真实账单、运行上游账本或完成云端部署；源码接口存在不代表集成已经通过。具体证据见研究报告。
