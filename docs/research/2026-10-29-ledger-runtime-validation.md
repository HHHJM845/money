# 账本运行验证

日期：2026-10-29  
范围：官方账本运行包、虚构交易及浏览器模拟，不含安卓采集端。

## 运行版本

- ezBookkeeping `v2.1.1`，页面显示提交 `3dcc316`。
- 官方 macOS ARM64 发布包，未修改上游源码和配置。
- SHA-256：`40b95b6062498069d24b59c7e4a61799fe5371e1c3570a3710c0c061dcb9deda`，与 GitHub 发布资产的 digest 一致。
- SQLite 数据与上游运行文件置于 `.local/ezbookkeeping/`。
- 本地入口：<http://127.0.0.1:8080>。

本轮创建的是隔离测试账号和虚构交易，没有连接银行、支付平台或券商。官方默认配置的监听地址是 `0.0.0.0`，不是仅回环监听；签名密钥也未配置。当前包用于测试，不是正式数据部署。按用户协议，本轮没有擅改监听、鉴权、API Token 或外部服务配置。

## 接口验证

执行 `node scripts/verify-ledger.mjs`。

| 检查 | 观察结果 |
| --- | --- |
| 网页可访问 | 返回 HTML |
| 注册独立账号 | 正常获得登录会话，凭据不打印到终端 |
| 创建账户 | 借记账户、信用卡、虚拟账户均成功 |
| 同事件顺序重试十次 | 均返回原账单 ID，只入账一次 |
| 同商户同金额的另一笔交易 | 生成不同账单 ID，保留第二笔 |
| 收入、支出、还款、转账 | 余额符合下表 |
| 收支汇总 | 收入 100 元，支出 90 元；还款和转账未计入消费 |

虚构数据使用人民币，接口整数金额按分传入。网页金额与接口余额相互核对：

| 账户 | 期初 | 测试变化 | 最终 |
| --- | --- | --- | --- |
| 招商借记账户（模拟） | 1,000 元 | 两笔各 20 元消费、收入 100 元、还款 50 元、转入零钱 30 元 | 980 元 |
| 招商信用卡（模拟） | 0 元 | 消费 50 元，随后还款 50 元 | 0 元 |
| 微信零钱（模拟） | 0 元 | 从借记账户转入 30 元 | 30 元 |

总资产与净资产均为 1,010 元，负债为 0 元。信用卡还款前的余额为 -50 元。

实际接口：

- `POST /api/register.json`
- `POST /api/v1/accounts/add.json`
- `GET /api/v1/accounts/get.json`
- `POST /api/v1/transaction/categories/add.json`
- `POST /api/v1/transactions/add.json`
- `GET /api/v1/transactions/statistics.json`

请求使用登录会话及 `X-Timezone-Name: Asia/Shanghai`、`X-Timezone-Offset: 480`。没有为了验证而开启 API Token。

## 网页验证

执行 `scripts/verify-browser.cjs`，依赖宿主提供的 Playwright 和本机 Chrome：

- 电脑视口：1440 × 960。
- 手机模拟：Playwright Pixel 7 设备配置；不代表一加 13 实测。
- 两端分别登录同一个测试账号，核对首页收入 100 元和支出 90 元。
- 电脑首页显示净资产 1,010 元；手机首页默认重点显示收支，账户页展示资产与账户。
- 进入账户页核对三类账户、名称及借记账户余额 980 元。
- 检查首页和账户页没有文档级横向溢出，过程中没有 `pageerror`。
- 截图关闭动画，避免截取移动端页面切换的中间帧。

首次自动化检查按电脑界面假定手机首页和路由，导致脚本失败。已通过直接查看页面内容核实差异，只修正测试定位、加载等待和页面导航，没有修改上游产品。

验证结果和截图保存在 `.local/ledger-verification.json`、`.local/browser-verification.json`、`.local/desktop-overview.png`、`.local/desktop-accounts.png`、`.local/mobile-overview.png` 和 `.local/mobile-accounts.png`。

## 明确的限制与下一步

默认重复提交检查使用内存，间隔为 300 秒。当前成功结果只证明短时间内的顺序重试，不证明并发创建、超时结果未知、进程崩溃或长期重放可靠。

下一阶段优先实现稳定事件 ID、持久接收记录、事件到账单 ID 映射与入账结果未知时的核对恢复，再接安卓通知来源。不能把短期 `clientSessionId` 检查当成最终可靠同步方案。
